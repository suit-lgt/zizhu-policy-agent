# 完整系统功能设计与交付差距

状态：设计稿（2026-11-06）；0.5（2026-11-07）已补真实账号闭环（注册／审核／重置／改密）、6 代理协同 trace、本地上传入库＋核文切块发布门禁与 `/login.html`，本文"缺口"章节中这三类已部分闭合，具体以 `docs/verification.md` 的 v0.5 记录为准。本文回答两件事：一是把"资助政策智能体"按企业交付标准应该做成什么功能，二是当前项目目录离这个标准还缺哪些文件与能力。
事实来源：`docs/design.md`（模块划分）、`docs/project-brief.md`（D-001—D-011）、`docs/verification.md`（实测结果）、项目目录实扫。文中"实测"指本机跑过，"规划"指未执行。

## 一、"完整"的判定标准

企业交付型系统不是"功能多"，而是四层都闭合，缺一层就交不出去：

| 层 | 判定问题 | 本项目对应 |
|---|---|---|
| 功能层 | 每个角色从进入到办完，是否有闭环路径 | 学生初判→复核→申诉；审核端待办→结论；管理端政策发布→回滚 |
| 非功能层 | 性能、可用性、降级、审计、隐私是否有量化口径 | 单次初判 P95 ≤2s；断网可用；审计只追加；不存家庭明细 |
| 文档层 | 需求、设计、接口、数据字典、测试、手册、验收是否齐全且与代码一致 | 见第六节差距矩阵 |
| 运维层 | 换机器能否一键起、出故障能否恢复、升级能否回滚 | Docker Compose、初始化脚本、备份恢复、回滚预案 |

一句话：功能是骨架，非功能是底线，文档是交付凭证，运维是可持续性。

## 二、设计方法（按资助主题切分）

资助业务天然是一条"政策生命周期"，横向按角色旅程切，纵向上每个功能必须同时落四样东西：数据表、接口、页面、验收口径。只有页面没有表和验收口径的，都是演示级，不算交付级。

1. **按政策生命周期切功能域**：采集→核文→切块→原子化→版本发布→判等→解释→复核→申诉→统计→归档。每一环都要有人负责、有状态、有留痕。
2. **按角色旅程切界面**：学生（自查自办）、辅导员（复核）、资助中心（政策与批次管理）、系统管理员（权限与审计）。同一能力在不同角色面前是不同页面，不能一套界面全角色通用。
3. **按风险切非功能**：资助涉及家庭经济信息与资格结论，风险集中在"错判""越权看到明细""改判无痕""政策过期仍生效"，所以审计、权限、版本锚定、免责声明必须做成硬约束（I-1—I-7），不是文案。

## 三、角色与场景

| 角色 | 核心场景 | 首版 | 交付版 |
|---|---|---|---|
| 学生本人 | 我是困难生，能申请哪些、要什么材料、去哪办 | 有（初判＋依据＋材料＋渠道） | 加问答、进度、复核申请、申诉、隐私授权 |
| 辅导员／班主任 | 我带的班里谁可能需要，材料齐不齐 | 无 | 待办、批量初筛、退回补材料、进度跟踪 |
| 学院资助管理员 | 本院名额与结论分布、异常件 | 无 | 院级看板、导出报送 |
| 学校资助中心 | 政策口径、批次、复核终审、统计 | 无 | 政策发布/回滚、批次管理、终审、报表 |
| 政策库管理员 | 政策采集、核文、原子化、字典维护 | 命令行（实测） | 网页工作台＋审核流 |
| 系统管理员／审计员 | 账号权限、审计查询、备份恢复 | 无 | 权限矩阵、审计检索、运维面板 |

## 四、功能域清单

优先级：P0＝演示与首版必需；P1＝试点必需；P2＝交付增强。

### A 政策知识库（P0）

|---|---|---|---|

| A2 | 文号／发布机关／生效日期人工核对工作台 | 无（全 `pending_verify`） | 每条政策有人核、有核对人、有核对时间，才可 `published`（I-7） |

### C 审核端（P1）

待办列表与领取、复核结论录入（通过／退回／补材料）、批量名单初筛、学院与学校两级看板、超时与异常预警、报送导出。验收口径：任一复核动作可回溯到原结论与当时依据版本（I-5）。

### D 管理端（P1）

账号与组织、角色权限矩阵（学生／辅导员／学院／资助中心／管理员／审计）、政策与项目配置、字段字典与标准参数、校级分档细则维护、审计日志检索、数据导出审批、统计报表（申请量、结论分布、退回率、平均处理时长）。验收口径：越权访问被拒且记审计；导出走审批。

### E AI 能力层（P0，边界受 `docs/ai-contract.md` 约束）

解释文案生成（结构化结论→人话，挂 AI 标识）、问答 RAG＋拒答、抽取辅助（结果必须人审）、三态 Provider（真实／离线规则／Mock）与降级、评测集与回归、超时与成本上限。硬约束：判等、引用拼装、权限、状态一律不经模型（D-004）。

### F 平台与运维（P0 交付必需）

| 编号 | 功能 | 现状 | 验收口径 |
|---|---|---|---|
| F1 | Docker Compose 一键起 | 无（Docker Desktop 已装但守护进程未运行） | 空机器 `docker compose up` 后 5 分钟内页面可用 |
| F2 | 初始化与种子数据 | 部分（SQLite 已有数据） | 冷启动可重建库与合成样例 |
| F3 | 健康检查与监控告警 | 部分（`/api/health`） | 探针、错误率、慢请求有阈值与告警 |
| F4 | 备份与恢复 | 无 | 备份可恢复到指定时间点，演练有记录 |
| F5 | 日志与脱敏 | 无 | 日志不含家庭明细与姓名（I-4） |
| F6 | 灰度与回滚 | 无 | 新版本可回退，政策版本与代码版本分开回滚 |

### G 安全合规（P0）

统一身份接入（首版可用本校账号，演示用合成身份）、传输与存储加密、个人信息最小化与留存期、审计不可删、等保要点自查、如覆盖中职需考虑未成年人信息。验收口径：能出一份"采集字段—用途—留存—销毁"的对照表，且与代码一致。

## 五、关键数据实体与状态机

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `policy_doc` | doc_no、issuer、effective_from、status、content_hash、raw_path | 状态：`pending_verify→verified→published→superseded→archived` |
| `policy_version` | version_id、快照、发布时间、发布人 | 任务必须锚定版本（D-005） |
| `policy_clause` | doc_id、clause_no、text、char_start/end、publishable | 只读事实来源 |
| `policy_atom` | atom_id、project、field、op、value、determinable、superseded | 判等唯一依据 |
| `field_dict` | code、type、values、source、version | 字典改版要回归 |
| `project` / `project_rule` | 满足路径、manual 原子、standards、materials、channel | 项目配置 |
| `triage_task` | task_id、policy_version、student_json（脱敏）、result_json、status | 状态：`triaged→reviewing→approved/returned→appealed→amended` |
| `task_item` / `evidence_ref` | 结论、clause_id、quote、偏移 | 一结论多依据 |
| `material_item` | 材料名、来源（条款／学校）、是否必需 | 解决 B3 无来源 |
| `review_event` / `appeal` / `audit_log` | 操作人、时间、前后值、理由 | 只追加不删除（I-5） |
| `qa_log` / `model_run` | 问题、命中条款、模型版本、耗时 | 问答可审计 |

现有落库只覆盖 `triage_task` 一张业务表（实测 3 行），其余为规划。

## 九、明确不做

不做资格认定与资金发放、不替代政务系统、首版不接真实身份、不做跨省政策全覆盖、不做模型自动判定结论、不保存原始录音与家庭明细。这些是边界，写进需求规格的"不做清单"，避免验收时被当作缺陷。

## 十、当前最硬的三个缺口
