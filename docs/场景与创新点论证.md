# 真实场景、痛点与创新点论证

> 用途：回答"这套系统到底给谁用、解决什么真问题、凭什么算创新"。全篇基于本系统已落地的代码与数据，不引用未经核实的市场统计；政策口径仅以已核文的 3 份文件为例（财教〔2021〕310 号、财教〔2024〕181 号、粤财规〔2026〕1 号）。

## 一、结论先行

**首版主用户是学生本人**：第一次申请国家助学金／励志奖学金前，想知道"我这样的情况大概能申请哪一档、要准备什么、依据是哪一条"。

家庭（家长）与高校教师（辅导员、资助中心老师）是同一套能力的不同入口：家长要"听得懂、能照着做"，教师要"答得快、答得一致、留得下依据"。

系统的差异化不在"多一个聊天框"，而在三件事同时成立：**政策文件是真的且经过人工核文、结论是确定性规则判出来的、每条建议都能点回原文与版本**。这三件事在通用大模型和传统资助表单里通常是缺的。

## 二、三个真实场景与痛点

### 场景 1｜学生本人：申请前的"自我判断"

**谁**：高职二年级学生，广东生源，家庭属于低保边缘，学校已做过困难认定但等级不确定；想申请国家助学金，也想知道能不能冲励志奖学金。

**真实动作**：先搜"国家助学金多少钱"，再翻学校通知群，再问学长，最后到资助中心现场问。中间会遇到：

- 同一个项目在不同文件里表述不同（国家文件说范围，省级文件说标准，学校细则说材料），**不知道哪份算数、哪份还有效**；
- 看到"原则上""可参照""由各地确定"，**不知道自己是"能申请"还是"要核实"**；
- 材料清单靠口口相传，**跑两三趟补齐**；
- 问通用 AI，回答很顺但**给不出文号和条款**，不敢拿去用。

**系统怎么接**：学生勾选隐私授权后填 12 个判定必需的原子字段（学籍、年级、困难认定、特殊困难、户籍等），系统用确定性规则给出"可申请／需核实／暂不适用"三档，每条挂至少 1 条已核文条款，点开看到条款原文与字符位置；缺字段就明确说"需核实"，不猜。材料清单与办理渠道按结论给出，导出件带政策版本与免责声明。

**为什么这是真痛点**：学生要的不是"更多信息"，而是**在跑腿之前知道自己该不该跑、带什么去**。这一步现在没人替他做。

### 场景 2｜家庭（家长）：听不懂、不敢填、怕泄露

**谁**：学生的家长，不熟悉政府网站，看到"家庭经济困难认定""共同生活家庭成员"等术语就停住；担心填了收入、残疾、孤儿等信息会被扩散。

**真实动作**：打电话问班主任，或让孩子自己去问；遇到需要上传证明材料时反复确认"要不要原件、会不会外传"。

**系统怎么接**：页面用"你家几口人、谁跟你一起生活、有没有低保证"这类口语字段；手机号只存脱敏形式，姓名不落库，日志不记家庭明细；答案里不出现"符合／不符合"，统一给"可申请／需核实"和线下渠道，避免家长把系统结论当成学校认定。

**为什么这是真痛点**：家长的核心诉求是**少跑一趟、别填错、别泄露**，不是"功能多"。

### 场景 3｜高校教师：一个人对几百个学生，口径还要一致

**谁**：二级学院辅导员或资助中心老师，开学两周内要回答上百条相似问题，还要处理复核、申诉与报送。

**真实动作**：在群里复制往年答复，遇到政策调整再手工改；学生拿系统截图来问"这个准不准"，老师要能当场指出依据；期末要出报送表。

**系统怎么接**：审核台有批量初筛、两级看板、超时预警；每条结论可回点原文，老师可以直接把条款链接发给学生；复核、申诉、改判全部留痕（I-5），报送 CSV 带统计口径；管理员可发布新政策版本并一键回滚，保证"今年和去年答的不一样"时有据可查。

**为什么这是真痛点**：老师缺的不是知识，而是**可复用、可追溯、可审计的答复载体**。

## 三、和现有产品的差别（按能力类型对比，不点名具体产品）

| 能力 | 学校资助表单／通知群 | 政务小程序／FAQ | 通用大模型 | 本系统 |
|---|---|---|---|---|
| 入口 | 提交申请，不解答"我够不够" | 关键词问答，答案固定 | 自然语言，但无出处 | 先初判三档，再给材料与渠道 |
| 政策时效 | 靠人工更新通知 | 靠栏目维护 | 训练数据滞后，无法核验 | 采集／本地上传→人工核文→切块→发布版本→可回滚 |
| 依据 | 通知截图 | 条款链接不一定到条 | 常无文号，易编 | 每条结论挂条款 ID＋原文＋字符位置，可回点 |
| 不确定时 | 让学生来现场 | 答"请咨询" | 仍然给确定口吻 | 明确"需核实"，并说明缺哪个字段 |
| 留痕 | 线下 | 无 | 无 | 复核／申诉／改判／发布全审计，禁改禁删 |
| 隐私 | 表单收全量信息 | 不一 | 对话内容不可控 | 只收判定必需字段，手机号脱敏，日志脱敏 |

## 四、三条创新点如何落地（对应代码，不是口号）

### 创新点 1：数据真实、可采集更新、可本地上传、人工核文、版本可回滚

- **真实**：条款来自官方栏目采集或本地上传，正文与原文偏移逐条校验；文号、发布机关、生效日期未核对不得发布（I-7）。
- **可更新**：采集器支持多栏目批量与增量差集；本地上传支持 `.docx／.pdf／.txt／.md`，同文件 SHA-256 去重。
- **人工在环**：上传只生成"待核文"草稿，核文→切块→发布三步缺一不可；未核文的上传草稿不进问答检索。
- **版本与回滚**：每次发布把该版本已核文条款与现行原子固化到快照（文件数／条款数／原子数＋版本号）；检索与判等只读当前版本快照，回滚切换 `current` 后问答与初判同时切回旧版内容，不删历史；导出件带版本号。

### 创新点 2：多智能体协同了解用户情况并给客观呈现

- 6 个职责单一的确定性代理：受理→判等→依据核验→表述→合规→汇总，不调模型，避免"模型自己编"。
- 受理代理先查字段完整度，缺关键字段直接降为"需核实"；依据核验代理真实回库比对 `clause_id` 与引文偏移，核不到就标失败；合规代理扫"符合／不符合／通过认定"等越界措辞。
- 每一步的输入摘要、状态、耗时写进 `trace`，学生端页面可见"6/6 个代理完成"，把"协同"从概念变成可观察的过程。

### 创新点 3：建议基于知识库、依据可追溯

- 引用由系统拼装，不由模型生成（I-3）；条款表存 `char_start/char_end`，`body_text[start:end]` 必须等于条款正文。
- 依据核验代理在每次初判时逐条回查，偏移或引文不符即判异常；问答只答命中条款，无命中明确拒答，不拿常识补。
- 版本号随结论落库，事后可回答"当时是按哪一版政策说的"。

## 五、边界（先说清，才好立住）

- 不做资格认定、不做资金发放、不接真实身份系统；结论只到"可申请／需核实"，最终以学校资助部门认定为准。
- 不替代学校通知与线下办理；系统给渠道与材料，办理仍走学校流程。
- 当前已核文的是 3 份核心政策，其余 16 份采集草稿仍待核；全局 `policy_verified=false` 的提示保留，避免把"部分核文"说成"全部核文"。

## 六、演示时怎么讲（用户自行操作，不写脚本）

1. 打开 `/login.html` 注册一个学生账号（昵称＋密码，学校／手机号选填），看到"待审核"和四步指引。
2. 切到 `/admin.html` 的「注册审核」，通过申请并指定角色；再到「账号权限」演示重置密码，拿到一次性临时密码。
3. 用该账号登录 `/`，填学籍与家庭情况，看到三档结论、依据条与 6 个代理的协同过程。
4. 在 `/admin.html` 的「文档入库」上传一份本地政策 Word，说明它只是"待核文"草稿；核文、切块、发布后学生端才按新版本作答，旧版本可回滚。

这条路径本身就是"真实账号—真实审核—真实判等—真实入库"的闭环，不需要旁白脚本也能讲清创新点。
